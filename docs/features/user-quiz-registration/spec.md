# 로그인 유저 퀴즈 등록 기능 기획

- 상태: Draft (검토 중)
- 관련 문서: [`ARCHITECTURE.md`](../../../ARCHITECTURE.md), [`apps/api/CLAUDE.md`](../../../apps/api/CLAUDE.md), [`apps/web/CLAUDE.md`](../../../apps/web/CLAUDE.md), [`docs/adr/0009-change-link-verification-trust-boundary.md`](../../adr/0009-change-link-verification-trust-boundary.md)
- **선행 조건**: [범용 알림 시스템](../notification-system/spec.md)이 먼저 완료돼야 한다. 알림의 스키마·API·UI(벨/드롭다운/상세 페이지)는 전부 그 문서·이슈에서 별도로 만들고, 이 문서는 그걸 다 쓰는 입장에서만 다룬다(직접 설계하지 않는다).

## 1. 배경 및 목적

현재 퀴즈는 [`QuizGeneratorService`](../../../apps/api/src/quiz/quiz-generator.service.ts)를 통해 운영진이 아티스트 단위로 전체 곡을 자동 생성하는 방식으로만 만들어진다. 곡을 직접 골라 나만의 퀴즈를 만드는 기능은 없다. 로그인한 유저가 원하는 곡을 검색해서 담고, 유튜브 구간과 정답을 직접 구성해 퀴즈를 등록할 수 있게 한다.

## 2. 유저 플로우 개요

1. `apps/web` 방 목록 화면에서 "퀴즈 만들기" 버튼을 누른다(비로그인 유저에게도 보이지만, 클릭 시 로그인 필요 안내).
2. 로그인 상태면 24시간 등록 제한에 걸려있지 않은지 그 자리에서 확인한다(걸려있으면 진입 자체를 막고 남은 시간을 안내).
3. 빌더 화면에서 곡을 검색해서 담는다(기존 DB 검색 우선, 없으면 "찾는 곡이 없어요" 버튼으로 멜론 검색). 곡을 선택하면 즉시 DB에 곡/아티스트/앨범 정보가 저장된다(이미 있으면 재사용).
4. 곡별로 유튜브 링크를 확인/수정하고, 정답 후보를 확인/수정한다 — 저장하는 즉시(모달을 닫는 즉시) 서버가 링크를 검증하고, 그 결과가 곡 카드에 반영된다.
5. 최소 5곡 이상, 모든 곡의 링크가 유효해야 최종 등록 버튼이 활성화된다.
6. "등록" 버튼을 누르면 퀴즈가 곧바로 만들어지고 공개되지만, 화면에는 "등록이 완료됐습니다"가 아니라 "등록 신청이 접수됐어요" 같은 문구가 뜬다 — 곡별 링크를 마지막으로 한 번 더 확인하는 절차가 화면 뒤에서(비동기로) 계속 진행 중이기 때문이다.
7. 그 백그라운드 확인이 끝나면(문제가 없었든, 드물게 곡이 하나 빠졌든) 유저에게 등록 완료 알림이 온다. 곡이 빠졌다면 알림에 어떤 곡이 왜 빠졌는지 적혀 있다.
8. 게임 진행 중 문의 기능을 통해 다른 유저가 신고할 수도 있다(신고 접수 경로만 우선 마련, 처리 로직은 추후 작업).
9. 유저는 마이페이지에서 본인이 등록한 퀴즈를 자유롭게 수정/삭제(soft delete)할 수 있다.

## 3. 상세 설계 (백엔드)

### 3.1 곡 검색

- 1차: 기존 DB(`SQ_SONG`/`SQ_ATST`)에서 제목/아티스트명으로 검색.
- 2차("찾는 곡이 없어요" 버튼): [`MelonScraperClient`](../../../apps/api/src/scraper/melon-scraper.client.ts)에 **신규 메서드**를 추가해 멜론 통합검색 결과를 스크래핑한다. 검색 결과 페이지에는 곡 ID, 곡명, 아티스트명뿐 아니라 **앨범 ID도 함께 노출되므로 이를 그대로 활용**해 앨범 정보 조회/생성까지 처리한다(신규 상세 페이지 스크래핑 불필요). 상위 10건을 "곡명 - 가수명" 형태로 응답한다.

### 3.2 신규 곡/아티스트/앨범 등록 (멱등 처리)

유저가 검색 결과에서 곡을 선택하면 그 즉시 저장한다.

- `Artist`: `melonAtstId` 기준으로 기존 레코드 있으면 재사용, 없으면 생성 ([`Artist.melonAtstId`](../../../apps/api/src/quiz/entities/artist.entity.ts)에 unique 인덱스 존재).
- `Album`: `melonAlbmId` 기준으로 동일하게 처리.
- `Song`: `melonSongId` 기준으로 동일하게 처리(unique 인덱스 존재).
- 동시 등록으로 인한 unique 충돌은 catch 후 재조회로 처리한다([`ScraperService`](../../../apps/api/src/scraper/scraper.service.ts)의 `getOrCreateArtistByMelonId` 패턴을 그대로 재사용/확장).
- 곡-아티스트 다중 연결은 기존 [`ArtistLinkService`](../../../apps/api/src/scraper/artist-link.service.ts)를 재사용한다.

### 3.3 유튜브 링크 처리

곡별 링크 소스 우선순위: **유저 직접 입력 > `Song.ytbLink` 기본값 > 공란(자동 등록 버튼으로 채움)**.

검증은 3단계다.

1. **클라이언트 형식 검증**: 입력 시점에 즉시 URL 형식(`youtube.com/watch?v=`, `youtu.be/`)을 확인하고, 형식이 안 맞으면 저장 자체를 막고 사유를 붉은 글씨로 안내한다(UX용, 신뢰 경계 아님).
2. **서버 형식 재검증**: [`ADR-0009`](../../adr/0009-change-link-verification-trust-boundary.md) 원칙에 따라 클라이언트 검증을 신뢰하지 않고 서버에서 호스트+경로+videoId를 다시 검증한다. 저장 값은 항상 videoId로 재구성한 URL을 사용한다(원본 그대로 저장 금지).
3. **서버 콘텐츠 검증**: 서버에서 해당 링크를 스크래핑해 영상 제목을 가져오고, "곡의 진짜 제목"(Feat/Prod 등 괄호 표기 제거 → 특수문자·공백 제거)이 "영상 제목에서 특수문자를 전부 제거한 문자열"에 포함되는지 러프하게 확인한다. 정규화 로직은 3.4의 정답 자동 생성과 공유하는 공용 유틸로 만든다.

**검증 시점은 두 곳이다** (4.4 참고):
- **곡별 즉시 검증**: 유저가 링크 편집 모달에서 저장하는 즉시 2·3단계를 실행하는 전용 엔드포인트(`POST /songs/:songId/youtube-link/validate`)를 호출한다. 이게 주 경로다 — 통과해야 카드가 ✅ 상태가 되고, 실패하면 카드에 사유가 표시되어 유저가 그 자리에서 고칠 수 있다.
- **최종 등록 시 재검증(안전망, 비동기)**: `POST /quizzes`는 이미 곡별 즉시 검증을 통과한 데이터로 퀴즈를 바로 생성하고 응답한다 — 이 응답을 기다리는 동안 사용자를 오래 붙잡지 않기 위해, 동일한 2·3단계 재검증은 **응답을 보낸 뒤 백그라운드에서** 돈다. 곡별 즉시 검증을 통과했더라도 그 이후 영상이 비공개/삭제되는 등 드문 경우(TOCTOU)에 대비한 마지막 방어선이다. 링크를 직접 입력한 곡이 많으면 이 백그라운드 검증에 시간이 걸릴 수 있다(곡마다 스크래핑 1회). 여기서 실패한 곡은 그 즉시 퀴즈에서 제외한다. 이 과정이 다 끝나면(제외된 곡이 있든 없든) [알림 시스템](../notification-system/spec.md)으로 등록 완료 알림을 보낸다 — 제외된 곡이 있으면 알림의 제목/내용에 어떤 곡이 왜 빠졌는지 포함한다.
- 백그라운드 검증에서 곡이 빠져 결과적으로 5곡 미만이 되더라도, 이미 등록된 퀴즈 자체를 취소하거나 곡 수를 사후에 다시 강제하지는 않는다(최소 5곡 조건은 최초 제출 시점에만 검사한다). 이런 경우가 흔치 않다고 보고 단순하게 처리한다.

**자동 등록 버튼**: 링크가 공란인 곡에 한해 기존 [`YoutubeScraperClient.search()`](../../../apps/api/src/quiz/youtube-scraper.client.ts)로 "{아티스트} - {곡명}"을 검색해 채운다. 이 결과는 (검색 자체가 아티스트+곡명 기준이라 신뢰도가 높으므로) 3.3-③ 제목 매칭 검증 대상에서 제외한다.

**최종 등록 조건**: 최소 5곡 이상이고, 모든 곡에 유효성 검증을 통과한 링크가 있어야 등록을 완료할 수 있다. 조건을 못 채우면 서버가 등록을 거부하고, 클라이언트도 사전에 등록 버튼을 막는다.

### 3.4 정답 처리

- 이미 시스템에 등록된 곡(같은 `songId`로 다른 퀴즈에 이미 정답이 있는 경우)은 기존 [`QuizSongReuseService`](../../../apps/api/src/quiz/quiz-song-reuse.service.ts)로 기존 정답을 디폴트로 노출한다.
- 유저는 노출된 정답을 자유롭게 추가/삭제할 수 있다.
- 처음 등록되는(정답 이력이 없는) 곡은 GPT 호출 없이, **규칙 기반으로 곡의 풀 제목**을 정답 후보로 자동 등록한다: 원제목 그대로 1개 + Feat/Prod 등 괄호 표기를 제거한 "진짜 제목" 1개(3.3-③과 동일한 정규화 유틸 재사용). 유저가 이후 추가/삭제 가능.

### 3.5 소유권 및 수정/삭제

- `Quiz`에 `CRT_USER_KEY`(nullable) 컬럼을 추가한다. 기존 운영진 생성 퀴즈는 `NULL`로 남는다.
- 본인이 등록한 퀴즈만 수정 가능(제목/설명/곡 구성/링크/정답 전체 범위) — 수정 시에도 3.3의 링크 검증을 동일하게 거친다.
- 삭제는 하드 삭제가 아니라 기존 `Quiz.useYn`을 `'N'`으로 바꾸는 soft delete로 처리한다(플레이 이력과의 정합성 유지).

### 3.6 신고

- **이번 단계는 신고 접수 경로만 마련한다.** 별도 신고 UI/API를 새로 만들지 않고, 게임 진행 중 이미 쓰이는 [`InquiryModal`](../../../apps/web/src/components/InquiryModal.tsx)의 "처리 가능한 요청" 안내 문구에 "부적절한 콘텐츠/저작권 문제 신고" 항목을 추가하는 정도로 반영한다(4.7 참고). 기존 `POST /inquiries` 흐름을 그대로 쓰고, 신고 성격의 문의를 실제로 분류·저장할 테이블(`SQ_QUIZ_REPORT` 등)과 그 처리 로직은 **추후 별도로 설계한다** — 지금 범위에는 포함하지 않는다.

### 3.7 등록 횟수 제한

- 유저당 **24시간 롤링 윈도우** 기준 1회. 마지막 "성공"한 등록 시각(`Quiz.crtDt` where `crtUserKey = 나`) 기준으로 계산하며, 검증 실패로 저장되지 않은 시도는 횟수에 포함하지 않는다.
- **조회 전용 API**(`GET /quizzes/registration-eligibility`)를 제공해, 빌더 화면 진입 전(4.1)에 미리 등록 가능 여부와 남은 시간을 확인할 수 있게 한다. 이 API는 안내용이고, 실제 강제는 `POST /quizzes` 시점에 서버가 한 번 더 검사한다(여러 탭에서 동시 시도하는 경우 등 대비).
- 제한에 걸리면 429와 함께 "N시간 M분 후 등록 가능합니다" 형태로 남은 시간을 안내한다.

## 4. UI/UX 설계 (`apps/web`)

기존 화면 스타일([`RoomListPage`](../../../apps/web/src/pages/RoomListPage.tsx), [`CreateRoomPage`](../../../apps/web/src/pages/CreateRoomPage.tsx))의 톤(퍼플 포인트 컬러, 흰 카드+shadow, `rounded-full` 버튼, 모달 기반 보조 UI)을 그대로 따른다. 새 컴포넌트 패턴(다단계 마법사, 토스트 등)은 만들지 않는다.

### 4.1 진입점 · 로그인 · 등록 가능 여부 확인

- `RoomListPage` 헤더의 "+ 새 방 만들기" 버튼 옆에 "+ 퀴즈 만들기" 버튼을 추가한다. 로그인 여부와 무관하게 항상 노출한다.
- 클릭 시:
  1. 비로그인이면 기존 비밀번호 입력 모달([`RoomListPage`](../../../apps/web/src/pages/RoomListPage.tsx) 참고)과 같은 톤의 모달로 "퀴즈 등록은 로그인 후 이용할 수 있어요" + "로그인하러 가기" 버튼을 보여준다(페이지 이동 없음).
  2. 로그인 상태면 `GET /quizzes/registration-eligibility`를 호출한다. 제한에 걸려 있으면 같은 톤의 모달로 "OO시간 후 등록할 수 있어요"를 보여주고 이동하지 않는다. 가능하면 `/quizzes/new`로 이동한다.

### 4.2 퀴즈 만들기/수정 빌더 페이지 (`/quizzes/new`, `/quizzes/:quizId/edit`)

- `CreateRoomPage`와 같은 단일 폼 페이지 톤. 제목/설명 입력 + "담은 곡" 카드 리스트.
- 수정 화면은 같은 컴포넌트를 재사용하고 기존 곡/링크/정답으로 프리필한다. 곡을 추가·삭제한 뒤 최종 저장 시 클라이언트가 계산한 최종 리스트를 그대로 서버에 보내고, 서버가 기존 구성과 대조해 추가/삭제를 반영한다 — 별도의 "변경 이력 diff" UI는 만들지 않는다.
- 등록/수정 버튼은 [3.3의 최종 등록 조건](#33-유튜브-링크-처리)(최소 5곡, 전체 곡 링크 검증 통과)을 만족할 때만 활성화된다.
- "등록"을 누르면 버튼이 "등록 신청 중..."으로 바뀐다. `POST /quizzes`는 백그라운드 안전망 검증을 기다리지 않고 곧바로 응답하므로 이 단계는 보통 금방 끝난다.
- 응답을 받으면 `/mypage`(내 퀴즈 탭)로 이동하며 "등록 신청이 접수됐어요. 처리 결과는 알림으로 알려드려요" 같은 문구를 보여준다 — "등록이 완료됐습니다"처럼 이미 다 끝났다는 뉘앙스는 쓰지 않는다. 실제 완료(일부 곡 제외 여부 포함)는 3.3의 백그라운드 검증이 끝난 뒤 알림으로 확정된다.

### 4.3 곡 검색 및 담기

- 인라인 검색창 + 결과 리스트(`CreateRoomPage`의 퀴즈 검색 리스트와 동일한 패턴).
- DB 검색 결과가 없으면 리스트 하단에 "찾는 곡이 없나요?" 버튼이 나타나고, 누르면 같은 자리에서 멜론 검색 결과로 전환된다(3.1).
- 이미 담은 곡은 검색 결과에서 선택 불가 처리(중복 추가 방지)하거나 "이미 담음" 표시로 비활성화한다.
- 각 곡 카드에는 삭제(빼기) 버튼을 둔다.

### 4.4 곡별 링크·정답 편집 (비동기 검증)

- 카드 클릭 시 [`EditRoomModal`](../../../apps/web/src/components/EditRoomModal.tsx)과 같은 모달 패턴으로 유튜브 링크 입력(형식 오류는 즉시 빨간 글씨)과 정답 태그 목록(추가/삭제)을 편집한다.
- "확인"을 누르면 모달은 바로 닫히고 카드가 "확인 중..." 상태(스피너)가 된다. 서버 검증(3.3의 ②③단계, `POST /songs/:songId/youtube-link/validate`)이 백그라운드로 진행되는 동안 유저는 다른 곡을 계속 편집할 수 있다.
- 검증 결과에 따라 카드가 ✅(통과) 또는 ⚠️(실패 사유 표시, 클릭 시 모달 재오픈)로 바뀐다.
- 링크가 공란인 카드에는 "자동으로 찾기" 버튼을 두어 3.3의 자동 등록 스크래핑을 트리거한다(이 결과도 로딩 스피너 → 완료 시 카드 갱신). 자동으로도 못 찾으면 "링크를 찾지 못했어요, 직접 입력해주세요" 안내.

### 4.5 임시 저장

- 빌더 화면의 진행 상태(담은 곡, 링크, 정답)를 `localStorage`에 임시 저장한다(기존 [`roomSession`](../../../apps/web/src/utils/roomSession.ts) 패턴 참고). 새로고침해도 복구된다.
- 페이지 안에 "작성 중인 내용은 이 브라우저에 임시 저장돼요. 브라우저 데이터를 지우거나 다른 기기로 접속하면 사라질 수 있어요" 안내 문구를 작게 둔다.

### 4.6 마이페이지 (`/mypage`, 신규)

- 이 앱에 없던 화면이라 새로 만든다. 탭 또는 섹션 두 개로 구성한다: "내가 등록한 퀴즈" / "알림"(알림 탭의 UI는 [범용 알림 시스템](../notification-system/spec.md)에서 만든 컴포넌트를 그대로 배치한다 — 이 문서에서 새로 설계하지 않는다).
- **내가 등록한 퀴즈**: 최신 등록순 정렬. 카드에 제목·곡 수·플레이 횟수(`Quiz.playCnt`)를 표시하고, 수정(`/quizzes/:quizId/edit`로 이동)·삭제 버튼을 둔다. 삭제는 확인 모달("정말 삭제할까요? 삭제한 퀴즈는 목록에서 사라져요" + 취소/삭제하기)을 거친다. 목록이 비어 있으면 `RoomListPage`의 빈 상태 패턴과 같은 톤으로 "아직 등록한 퀴즈가 없어요" + 퀴즈 만들기 버튼을 보여준다.

### 4.7 신고

- 게임 진행 중 [`InquiryModal`](../../../apps/web/src/components/InquiryModal.tsx)의 안내 문구(현재 3개 항목: 재생 시작 지점/링크 오류/정답 추가)에 "부적절한 콘텐츠나 저작권 문제가 있어요 (신고)" 항목을 추가한다. 새 UI 요소나 API 변경은 없다 — 3.6 참고.

## 6. API 개요 (초안, 구현 단계에서 세부 조정)

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/melon/songs/search?keyword=` | 멜론 곡 검색 상위 10건 |
| POST | `/songs/from-melon` | 검색 결과 선택 시 곡/아티스트/앨범 멱등 저장 |
| GET | `/songs/:songId/answers` | 기존 정답 목록(등록 화면 디폴트 노출용) |
| POST | `/songs/:songId/youtube-link/validate` | 유저 입력 링크 즉시 검증(형식+콘텐츠 매칭) — `UserAuthGuard` |
| POST | `/songs/:songId/youtube-link/auto` | 링크 공란 곡에 대해 자동 스크래핑 |
| GET | `/quizzes/registration-eligibility` | 24시간 등록 제한 상태 조회 — `UserAuthGuard` |
| POST | `/quizzes` | 퀴즈 등록 신청(24시간 제한, 최소 5곡) — 곧바로 응답하고, 링크 안전망 재검증은 응답 후 백그라운드에서 진행 후 완료 알림으로 결과 통지 — `UserAuthGuard` |
| PATCH | `/quizzes/:quizId` | 본인 소유 퀴즈 수정 — `UserAuthGuard` + 소유자 검증 |
| DELETE | `/quizzes/:quizId` | 본인 소유 퀴즈 soft delete — `UserAuthGuard` + 소유자 검증 |

알림 관련 API는 [알림 시스템 3장](../notification-system/spec.md)을 따른다.

## 7. 작업 단계

**착수 전 선행 조건**: [범용 알림 시스템](../notification-system/spec.md)의 스키마·API·UI(벨/드롭다운/상세 페이지)가 먼저 완료돼 있어야 한다. 아래 5번(퀴즈 등록 신청 API)이 그 알림 시스템을 호출만 하는 소비자이기 때문이다 — 알림 시스템이 없으면 5번을 끝까지 구현할 수 없다.

### 백엔드

1. **스키마**: `Quiz.CRT_USER_KEY` 컬럼 마이그레이션.
2. **멜론 곡 검색 + 곡 등록**: 멜론 통합검색 스크래핑, 곡/아티스트/앨범 멱등 저장 API.
3. **유튜브 링크 검증**: 서버 형식 검증 + videoId 정규화 + 제목 정규화 공용 유틸 + 콘텐츠 매칭 검증(즉시 검증용 API 포함), 자동 스크래핑 버튼 API.
4. **정답 처리**: 기존 정답 재사용 노출 API, 규칙 기반 정답 자동 생성 유틸.
5. **퀴즈 등록 신청 API**: 24시간 제한(+ 조회 전용 API), 최소 5곡 검증까지 확인되면 곧바로 퀴즈를 만들고 응답한다. 응답 이후 백그라운드에서 안전망 재검증(실패곡 제외)을 수행하고, 끝나면 결과(제외 곡 유무와 무관하게 항상)를 [알림 시스템](../notification-system/spec.md)의 알림 생성 함수를 호출해 전달한다(알림 자체의 스키마/API는 만들지 않고 이미 있는 걸 호출만 함).
6. **소유권 기반 수정/삭제 API**.

### 프런트엔드 (`apps/web`)

7. 진입점 + 로그인 필요 모달 + 등록 가능 여부 사전 확인 (4.1).
8. 퀴즈 만들기/수정 빌더 페이지 골격 + 최소 5곡·링크 검증 통과 조건 (4.2).
9. 곡 검색 UI(DB → 멜론 폴백) + 중복 방지 (4.3).
10. 곡별 링크·정답 편집 모달 + 비동기 검증 카드 상태 + 자동 링크 버튼 (4.4).
11. 로컬스토리지 임시 저장 (4.5).
12. 마이페이지(`/mypage`) — 내 퀴즈 목록(수정/삭제) 뼈대. "알림" 탭은 [알림 시스템](../notification-system/spec.md) 쪽 작업에서 만든 컴포넌트를 배치만 한다 (4.6).
13. 신고 안내 문구 변경 (4.7).

## 8. 남은 확인 사항

- 없음 — 논의를 통해 모두 확정됨. 구현 중 세부 사항(정규식 패턴, 카드 레이아웃 등)에서 추가 확인이 필요하면 이 문서를 갱신한다.
